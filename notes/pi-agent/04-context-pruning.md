# 04 - Context Compression（上下文剪枝与 Token 瘦身机制详解）

## 一、 上下文瓶颈与 Token 痛点

在长时间运行的 Agent 任务中（如大型代码重构、跑完 100 个单元测试）：
* 大模型的 **Context Window（上下文窗口）是有上限的**（例如 128k / 200k Tokens）。
* **每一次循环**，框架都需要把之前所有的对话历史和工具返回打包发给 LLM。
* 如果 Agent 执行了一次 `npm test` 或 `cat log.txt` 得到了 **5000 行终端输出**：
  * **不处理后果**：后面每一轮循环都要重复带着这 5000 行日志，Token 消耗呈指数爆表，且极其容易导致模型“迷糊”（Attention 机制退化）。

---

## 二、 三大剪枝与压缩机制详解

### 机制 1：保留头尾截断（Truncation & Pruning）
针对巨幅日志输出（如终端报错、大文件读取）：

```text
[原始输出 5000 行日志]
   ↓ 自动剪枝算法
[前 50 行: 启动命令与环境信息]
... ✂️ [已自动剪枝: 省略了中间 4900 行冗余日志] ...
[后 50 行: 最终的 Error 堆栈与失败断言]
```

* **为什么可行？**
  * **头部**：告知大模型“调用了什么命令”。
  * **尾部**：包含真正的报错堆栈（Stack Trace）与失败原因。
  * **中间**：全是重复的 `PASS test_1` 或进度的垃圾信息，丢弃对 Agent 思考**毫无影响**。

---

### 机制 2：滚动摘要（Rolling Summary / Compaction）
针对跑了几十轮的长对话：
* 当历史消息超过一定轮数（如 30 轮），Agent 会在后台触发一次“压缩任务”：
  * 大模型生成一段摘要：`“前情提要：已经完成了 src/user.ts 的算法重构，目前正在解决 src/auth.ts 的类型错误。”`
* 用这段 **100 字的精简摘要**，替换掉前面占用了 **50,000 字** 的旧历史消息。

---

### 机制 3：自愈式精准索要（Selective Retrieval / Grep）
如果中间被省略掉的部分正好包含了关键报错怎么办？
* 框架在剪枝时会在日志中显式标明 `... (中间省略 3000 行) ...`。
* 大模型如果发现尾部信息不足以定位 Bug，它会主动通过 `bash` 工具再发一条精准过滤指令：
  ```bash
  grep -C 5 "Exception" server.log
  ```
* 这样它就能精准拿回所需的信息，而无需把 3000 行日志全读进上下文。

---

## 三、 总结

上下文剪枝与压缩，是 AI Agent 能够做到**“长时自治运行（Long-running Agent）、持续跑几小时不爆 Token、不发懵”**的核心工程支撑。
