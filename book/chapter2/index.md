# 第2章 上下文工程

## 先看结论

这一章讲的是：**Agent 不是只靠模型聪明，更多时候要靠上下文设计得好。**

上下文工程就是在想一件事：

> 要把什么信息，以什么顺序，以什么格式，放给模型看，才能让它更稳地做事？

## 什么是上下文

上下文不是只有聊天记录。

它通常包括：

- 用户当前的问题
- 之前的对话内容
- 系统规则
- 工具说明
- 任务状态
- 记忆
- 外部资料

你可以把上下文理解成模型“正在看的桌面”。

桌面上放的东西越清楚，它越容易做对。

## 为什么这一章重要

很多人会以为，Agent 能力主要看模型有多强。

但实际情况是：

- 模型很强，不代表任务就能做好
- 如果上下文乱，模型也会犯错
- 如果上下文组织得好，中等模型也能做得很稳

所以，上下文工程往往决定了 Agent 的上限。

## API 里的上下文长什么样

这一章还讲了模型 API 的消息结构。

最常见的是这些角色：

- `system`：开发者给的规则
- `user`：用户输入
- `assistant`：模型输出
- `tool`：工具执行后的结果

你可以把它想成一段有顺序的工作记录。

模型不是凭空记住一切，而是通过这些消息来理解当前任务。

## KV Cache 是什么

这一章也讲了 `KV Cache`。

你可以先简单理解成：

**模型会把前面算过的内容先存起来，这样下一轮就不用重算全部。**

这能省时间，也能省钱。

但是它有一个很重要的要求：

**前缀最好不要乱改。**

如果你每次都改系统提示词，比如加一个会变化的时间戳，缓存就可能失效，速度会变慢。

## 提示工程在做什么

提示工程就是优化 `system prompt`。

它要解决的问题是：

- 让模型知道自己的身份
- 让模型知道要遵守什么规则
- 让模型知道输出应该长什么样
- 让模型知道怎么完成任务

你可以把系统提示词当成“员工手册”。

手册写得清楚，新员工才知道怎么做。

## Skills 是什么

当任务越来越多，只靠一个很长的提示词会越来越乱。

所以这章引入了 `Skills`。

你可以把 Skills 理解成：

**按需加载的小能力包。**

需要什么，就加载什么，不要一开始把所有东西都塞进去。

这样可以：

- 省 token
- 减少干扰
- 让上下文更清楚

## Agent 状态栏

这一章还提到一个很实用的想法：`Agent 状态栏`。

它的作用是把一些动态状态明确地放进上下文里，比如：

- 当前任务进度
- 已完成了什么
- 还有什么没做
- 当前环境状态

这样 Agent 不容易忘记自己做到哪一步了。

## 上下文压缩

任务越长，上下文就越容易变大。

所以还需要压缩。

压缩不是简单删字，而是：

- 把重要内容保留住
- 把重复内容去掉
- 把杂乱内容整理成更高密度的表达

重点不是“越短越好”，而是“保留关键信息”。

## 一个简单例子

比如你在做代码修复。

如果上下文里只放一句“修复 bug”，模型很难做对。

但如果你给它这些信息：

- 哪个文件出问题
- 哪条报错出现了
- 哪些规则不能违反
- 之前改过什么

它就更容易修对。

这就是上下文工程的价值。

## 这一章最想告诉你什么

上下文不是背景板。

它是 Agent 能力的一部分。

**给模型看什么，比模型本身有多强，往往更重要。**

## 记住一句话

上下文工程的核心不是“塞更多信息”，而是“把对的信息，用对的方式放给模型看”。
